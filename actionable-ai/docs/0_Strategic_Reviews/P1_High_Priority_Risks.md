# P1: High Priority Risks (Core UX & Functionality)

*Priority Level: P1 (High)*
*Urgency: Required for MVP Launch*
*Nature: These risks will not bankrupt the company, but they will result in a terrible user experience, broken core functionality, or massive customer churn if ignored.*

---

## 1. The "Codebase-to-Customer-Doc" Delusion
*   **The Risk:** Assuming an LLM can read raw `.ts` or `.py` files and reliably generate user-facing workflows (e.g., "How a customer changes their billing cycle"). Raw code lacks user workflow context, meaning the generated docs will be useless for end-users.
*   **The Fix:** Split the documentation pipeline. Raw code is strictly used to generate *Technical Docs*. *Customer-Facing Docs* are explicitly generated by analyzing Pull Request descriptions, Jira tickets, and uploaded PDFs.

## 2. Latency-Driven UX Friction
*   **The Risk:** LLMs are slow (3-8 seconds to process context, decide to use a tool, generate JSON arguments, and stream back). If a user asks the AI to perform an action (e.g., "Switch to dark mode"), waiting 8 seconds for the screen to react is terrible UX. Users will abandon the feature.
*   **The Fix:** Mandated **Optimistic UI / Streaming Tool Calls**. The widget must instantly show a loading state (e.g., "AI is executing...") so the user knows their request was heard immediately while waiting for the LLM overhead.

## 3. Widget Bundle Size Destroying Client SEO (Core Web Vitals)
*   **The Risk:** If the widget is built using heavy frontend libraries (full React, heavy markdown parsers, massive CSS bundles), it will increase the client's page load time. This destroys their Core Web Vitals (LCP) and SEO rankings, leading to immediate uninstalls.
*   **The Fix:** Restricted the frontend widget tech stack. It must be strictly optimized, built using **Vanilla JS or Preact**, with zero heavy dependencies, and loaded asynchronously via CDN.

## 4. The "Lost in the Middle" RAG Problem (Context Exhaustion)
*   **The Risk:** If a client has massive documentation, simple vector search returns lots of slightly relevant chunks. Stuffing too many chunks into the context window causes LLMs to suffer from the "Lost in the Middle" phenomenon (forgetting information in the middle of the prompt) resulting in hallucinations.
*   **The Fix:** Implemented a **Re-ranking Pipeline** (e.g., using Cohere ReRank). After retrieving the top 20 chunks from the Vector DB, a faster model re-ranks them based on exact relevance, and only the top 3-5 chunks are fed into the final LLM prompt.

## 5. Brittle Tool Registration
*   **The Risk:** Frontend code changes constantly. If a developer changes a JS function but forgets to update the AI's registration, the bot breaks silently and fails to execute actions.
*   **The Fix:** Added **Graceful Tool Failure** to the UI, ensuring it alerts the user and falls back to text if a registered JS function breaks. Added strict **Tool Schema Validation** to the backend.

## 6. Stale Knowledge on Deleted Features (Data Integrity)
*   **The Risk:** The auto-ingestion pipeline runs on `git push`. If a client deletes a feature and removes the code, but the Vector DB chunks aren't explicitly deleted, the AI will still tell users the feature exists because the old embeddings are still active.
*   **The Fix:** The Vector DB synchronization logic must handle *deletions* and *updates*. The backend needs a strict `diff`-based embedding update strategy (tracking file hashes) rather than blindly appending new chunks.

## 7. Third-Party API Failures (System Resilience)
*   **The Risk:** The AI can call client backend APIs. If a client's API goes down, returns a 500 error, or rate-limits our agent, the AI might hallucinate a success message or crash the conversation loop if it doesn't know how to handle the error.
*   **The Fix:** The API Request Engine needs a resilient retry mechanism (Exponential Backoff). Furthermore, the LLM system prompt must contain explicit instructions on how to gracefully explain non-200 HTTP responses to the user.

## 8. Denial of Wallet (DoW) via Agentic Tool Loops
*   **The Risk:** A malicious user figures out how to trick the agent into a recursive loop (e.g., "Call tool X. Output of X requires calling Y. Y requires calling X"). The agent gets stuck in a multi-turn tool-calling loop for 50 iterations, costing us massive token usage and locking up a backend thread.
*   **The Fix:** The agent orchestrator must enforce a strict `max_iterations` limit (e.g., max 5 tool calls per user prompt) and throw an exception to halt the loop.

## 9. Malicious Input Overflow (Context Crashes)
*   **The Risk:** A user writes a script to paste a 100,000-word prompt into the chat widget. If passed directly to the embedding model or LLM without chunking, we either crash the embedding model (OOM) or get a 400 Bad Request from the LLM provider, resulting in a broken UX.
*   **The Fix:** The backend must enforce hard token limits on user input (e.g., truncate user messages to max 2,000 tokens) *before* processing begins.
